# Go, for a Java developer building grazhda

You write Java every day. You know Maven, you know Spring, you know how to shape an object model. You have never written a line of Go, and you are about to write two Go programs from scratch: `zgard`, a command-line tool, and `dukh`, a background daemon that speaks gRPC.

This guide teaches Go from zero and assumes everything you already know. It will not explain what a loop is. It will explain, at length, why Go has only one loop keyword, why a method can quietly operate on a copy of your struct, and why the code you are about to write will be full of `if err != nil`.

Every example is taken from the real grazhda source, simplified only where the full version would bury the point. The Go side of the project is three modules joined by a `go.work` file: `libs/` holds the shared domain (configuration, workspace targeting, cloning and pulling repositories, cross-repository search, a package registry with a dependency DAG); `cli/` is `zgard`, a Cobra command tree; `daemon/` is `dukh`, a gRPC server that scans repositories on a timer and answers health queries.

# Part 1 — Why Go looks like this

## 1.1 One binary, no runtime

`go build` produces a single executable file. Not a jar, not a directory of jars, not a jar plus a JVM. One file, statically linked by default, containing your code, every library you imported, and the Go runtime itself — the scheduler, the garbage collector, the allocator.

For `zgard` this is the whole argument. A CLI written in Java needs a JVM of a compatible version on the user's machine, or a fat installer that ships one; it pays a couple of hundred milliseconds of startup on every invocation, which a user notices when they run `zgard config get` in a shell loop; and it carries a classpath, a runtime concern that can fail at runtime. A Go CLI is `curl`-and-`chmod +x`, starts in single-digit milliseconds, and has no classpath because every symbol was resolved at link time. For `dukh` the same property means the deployment unit is a file you can copy into a `FROM scratch` container or drop into `/usr/local/bin` under systemd.

Cross-compiling is two environment variables:

```bash
GOOS=linux GOARCH=arm64 go build -o bin/dukh ./cmd
```

That produces a Linux ARM64 binary from a macOS laptop with no cross-toolchain and no Docker, because the standard library is compiled from source for whatever target you name.

The cost is real. Binaries are large — a Cobra-based CLI is comfortably 10–20 MB. There is no hot-swapping of classes, no runtime bytecode generation, no agent attaching to a running process to rewrite behaviour. If Java's instrumentation and dynamic-proxy machinery is load-bearing for how you build software, Go took those tools away deliberately.

## 1.2 Compilation speed as a design constraint

Go was designed around a specific complaint: builds of large C++ services took long enough that engineers lost their train of thought. Several language decisions exist purely to make the compiler fast. Unused imports and unused local variables are compile *errors*, which keeps the dependency graph honest and lets the compiler skip work. There is no header-file model — a package's exported interface is recorded in its compiled object, so compiling a package that imports twenty others reads twenty small summaries rather than re-parsing twenty source trees. There is no inheritance hierarchy to resolve and no method overloading to disambiguate.

The practical result: a clean build of all three grazhda modules takes seconds, an incremental build after editing one file takes well under a second, and `go test ./...` for a package is fast enough to bind to a keystroke. You will edit-compile-test at a rhythm that in Java you only get from an already-warm incremental compiler.

## 1.3 What Go deliberately does not have

Read this as "things you will reach for and not find."

**No classes.** There are structs, and functions with a receiver. Methods are declared separately, at package level, attached to a type. There is no implicit `this`; the receiver is a named parameter.

**No inheritance.** No `extends`, no base class, no `protected`. Go offers *embedding*, which is composition with automatic method forwarding — it looks a little like inheritance and behaves nothing like it, because there is no virtual dispatch from an embedded type back into the outer type.

**No exceptions.** A function that can fail returns an error as its last value. No `throws`, no stack unwinding, no `try`/`catch`, no checked-versus-unchecked distinction, no `finally` (there is `defer`, which is better for the job). This is the largest day-one adjustment from Java.

**No constructors.** There is no function the compiler calls when a value is created. The convention is a plain `New`-prefixed function. And `Reporter{}` is always a legal value, which is why *zero values* matter enormously in Go and not at all in Java.

**No generics, for the first twelve years.** They arrived in Go 1.18. The ecosystem grew up without them, the standard library is mostly not generic, and idiomatic Go still reaches for interfaces first. grazhda uses none of its own.

**One loop keyword.** `for`. Three clauses is a C loop, one condition is a while loop, bare is infinite, `for … range` iterates.

**No ternary operator, no operator overloading, no implicit numeric conversion, no method overloading, no default parameters, no annotations.** Each is a place where Java lets you write something more compactly and Go decided the compactness was not worth the ambiguity at the reading end.

## 1.4 What this optimises for

Go optimises for the person reading unfamiliar code in a large codebase under time pressure, not the person writing it. Because there is no overloading, `rep.Record(res)` resolves to exactly one function, findable by grep. Because there is no inheritance, the method that runs is the one you can see on the type. Because there are no exceptions, every failure point is visible at the call site as an `err` you must do something with — there are no invisible control-flow edges out of the middle of a function. Because there is one formatter with no options, diffs contain only semantic changes.

What it sacrifices is expressive compression. Java lets you build a `ValidationRule` hierarchy with a fluent DSL and an annotation processor and express a validation suite in twenty declarative lines. Go's answer to the same problem, in `libs/config/config.go`, is a hundred-line function with nested `for` loops appending strings to a slice. The Go version is longer, duller, and utterly transparent to someone who has never seen it. That is the philosophy in one comparison. Go code is boring on purpose; writing clever Go is almost always a mistake.

# Part 2 — Getting a working setup

## 2.1 Install and verify

Install from <https://go.dev/dl>. Distribution packages are often behind, and grazhda's modules declare `go 1.26.1`, so take a recent toolchain.

```bash
$ go version
go version go1.26.1 linux/amd64
```

One toolchain serves the whole machine; there is no per-project Go install the way you keep several JDKs around. The `go` directive in `go.mod` states the *minimum* language version a module needs, and since Go 1.21 the toolchain will download a newer Go automatically if a module requires one.

You get a little state under `$HOME/go`: `pkg/mod` is the module cache (Go's `~/.m2/repository`, but read-only and verified), and `bin` is where `go install` puts binaries — put it on your `PATH`. `go env` shows the rest.

## 2.2 GOPATH, and why you can forget it

Before Go 1.11, all Go source on a machine lived under one `$GOPATH/src` tree and a package's import path was its position in that tree. You could not check a project out wherever you liked, and there were no versions: `go get` fetched the tip of a default branch and that was your dependency, forever. Reproducibility needed a third-party vendoring tool, of which there were several incompatible ones.

Modules replaced all of it, and since Go 1.16 they are the only mode. A project lives wherever you put it, its identity comes from the `module` line in its own `go.mod`, and versions are recorded and checksummed. You will still meet `GOPATH` in old blog posts; check the date and move on. The only surviving piece is the install destination, better set explicitly as `GOBIN`.

## 2.3 `go mod init` and the shape of `go.mod`

A module is the unit of versioning and dependency — roughly a Maven artifact.

```bash
$ cd libs && go mod init github.com/vhula/grazhda/libs
go: creating new go.mod: module github.com/vhula/grazhda/libs
```

The module path is not a URL you must own, but it should be where the code can be fetched from, because that is how another project's `go get` resolves it. It plays the role of `groupId:artifactId` and is also the import prefix for every package inside. Here is grazhda's `libs/go.mod`, cut down:

```
module github.com/vhula/grazhda/libs

go 1.26.1

require (
	github.com/fatih/color v1.19.0
	google.golang.org/grpc v1.80.0
	gopkg.in/yaml.v3 v3.0.1
)

require (
	github.com/mattn/go-isatty v0.0.20 // indirect
	golang.org/x/text v0.33.0 // indirect
)
```

Four differences from Maven. **There is one flat file per module** — no parent POM, no `dependencyManagement`, no profiles, no plugin configuration; build settings live in command-line flags and in the source. **Version selection is not "newest wins"**: Go uses Minimal Version Selection, taking the maximum of the minimum versions anything in the graph requires and no higher, so builds do not change because upstream published something new and upgrades are explicit edits. **Indirect dependencies are listed too**, so the whole graph is reproducible from `go.mod` alone. And **there is no `<scope>test</scope>`** — one dependency set per module, which the community mitigates by testing with the standard library and almost nothing else.

## 2.4 `go.sum`

```
github.com/fatih/color v1.19.0 h1:1AtrkAV5W1lS4Ux/L4aiEcZ9Q9Sf1Mm+8dcRnZLpHXk=
github.com/fatih/color v1.19.0/go.mod h1:UpG3RM1SzC/8/uAJ2f9Tt4z9Ab7Y5CkgV6MBIkD4rGE=
```

Two hashes per dependency — the module zip and its `go.mod` — verified on every build. It is Maven's checksum files, except mandatory, committed, and covering the whole graph. If a published version is ever altered in place your build fails loudly. Commit it; never edit it by hand.

## 2.5 The commands you will actually run

`go get <module>@<version>` adds or changes a requirement. `go install <module>@<version>` builds a binary into `$GOBIN` without touching the current module — this is how you get tooling such as `protoc-gen-go`.

`go mod tidy` is the housekeeping command with no Maven equivalent: it walks every import in every `.go` file including tests, adds what is required but unlisted, removes what is listed but unused, and refreshes `go.sum`. Run it after adding or deleting imports.

`go build` compiles; `./...` means every package below here. With a `main` package it writes an executable, with a library package it type-checks and caches.

```bash
$ cd cli && go build -ldflags "-X main.version=$(git describe --tags --always --dirty)" -o ../bin/zgard .
```

That `-ldflags` trick sets the package-level `var version = "dev"` in `main` at link time, replacing a whole category of Maven resource filtering.

`go run .` compiles to a temporary location and executes. `go test ./...` runs every test in the module, caching results per package — an unchanged package prints `(cached)` and runs nothing.

`go vet` is a static analyser in the toolchain, catching things the type system cannot: `Printf` format strings that do not match their arguments, locks copied by value, unreachable code, malformed struct tags. It reports only high-confidence problems, so treat its output as errors. It runs automatically as part of `go test`.

## 2.6 Formatting is not a matter of taste

`gofmt` has no configuration. No line length, no indent width, no brace style, no import-ordering options. It reads Go and prints Go, and there is exactly one output for any input.

```bash
$ gofmt -l .     # list unformatted files
$ go fmt ./...   # rewrite them, package-aware
```

This is not a preference the community happens to share; it was a decision to delete a category of argument. There are no formatting sections in Go code reviews, no checkstyle config to negotiate, no reformat-the-world commits. Every editor's Go plugin runs it on save, and you will quickly stop thinking about whitespace: you type roughly-correct code, hit save, and it snaps into shape.

Two consequences. Go indents with tabs and you do not get a vote. And `gofmt` aligns adjacent struct field types and tags into columns, which is why the config structs below look the way they do — you did not type those spaces and you must not fight them. Beyond `go vet`, add `golangci-lint` when the project grows; grazhda's `//nolint:gosec` comments are its suppression syntax.

# Part 3 — The language, for someone who knows Java

## 3.1 Packages and the directory rule

A package is a directory. Every `.go` file in one directory declares the same package name, and files in different directories are always different packages. `libs/config` and `libs/config/internal` have no relationship beyond the filesystem.

```go
// libs/config/config.go, errors.go and query.go all begin:
package config
```

Three files, one package. Everything declared in any of them is visible to the others with no import and no qualification. **The compilation and visibility unit is the directory, not the file**, so Java's one-public-class-per-file rule has no equivalent — split a package into files however helps a reader.

Imports name the full module path, and the last element is the identifier:

```go
import (
	"fmt"
	"sync"

	"github.com/vhula/grazhda/libs/config"
	clr "github.com/vhula/grazhda/libs/color"
)
```

Standard library first, blank line, then everything else; `gofmt` sorts within each group. You refer to imported names as `config.Workspace`. There is no wildcard import and no way to drop the qualifier, which is why a Go file's imports tell you honestly what it depends on. You can rename an import, as grazhda does for `color` → `clr`. Package `main` is special: it produces an executable and its `func main()` is the entry point.

## 3.2 Exported means capitalised

There is no `public`, `private` or `protected`. An identifier starting with an upper-case letter is visible to importers; anything else is visible only inside its own package. This applies to types, functions, methods, struct fields, constants and package variables.

```go
type Reporter struct {
	out    io.Writer
	errOut io.Writer

	mu      sync.Mutex
	results []OpResult
	total   int

	// ShowElapsed prints per-repository elapsed time after the message.
	ShowElapsed bool
	Quiet       bool
}
```

`out`, `mu`, `results` and `total` are invisible outside package `reporter`; `ShowElapsed` and `Quiet` are the deliberate public knobs. Two surprises follow. Visibility is package-scoped with no finer grain, so within a package everything sees everything — there is nothing like Java's private-between-two-classes-in-one-package. And capitalisation is load-bearing at a distance: reflection-based encoders such as YAML and JSON only ever see exported fields, which matters in section 3.15.

## 3.3 Declarations, `:=`, and the zero value

```go
var cfg Config                       // zero value
var period time.Duration = 5 * time.Minute
port := 50501                        // inferred as int
```

`:=` declares and assigns with inference, and works only inside functions.

Now the important half. **Every declaration without an initialiser gets the zero value of its type, and the zero value is always well defined:** `0` for numerics, `false` for `bool`, `""` for `string`, `nil` for pointers, interfaces, funcs, channels, maps and slices, and for a struct, every field at its own zero value.

`var cfg Config` gives a fully-formed `Config` — `Editor` is `""`, `Port` is `0`, `Workspaces` is a nil slice. Nothing is uninitialised, and nothing is null in the Java sense: a `string` field cannot be `nil`, so `len(ws.Name)` is always safe and `ws.Name == ""` is the only emptiness check you need. This is why Go has no constructors and no `Optional`. `sync.Mutex{}` is an unlocked mutex, which is why the `mu` field inside `Reporter` needs no initialisation — `reporter.New` never mentions it and it works:

```go
func New(out, errOut io.Writer) *Reporter {
	return &Reporter{out: out, errOut: errOut}
}
```

The design instruction hidden here is **make the zero value useful**. Ask what `var x YourType` should mean and try to make it the sensible default. `RunOptions{}` means "no dry run, not parallel, no filters", which is why so much of grazhda's test suite reads `workspace.RunOptions{}`.

Nil still exists and nil dereferences still panic, but the surface area is far smaller than Java's, because the things most often null in Java — strings, collections, small value objects — are not pointers in Go.

Constants are compile-time only and untyped by default, which lets them adapt to context:

```go
const (
	StructureTree = "tree"
	StructureList = "list"
)
const DefaultMonitoringPeriodMins = 5
```

`DefaultMonitoringPeriodMins * time.Minute` compiles because the untyped constant takes its type from the multiplication. A typed `int` would not — see 3.17.

## 3.4 Structs and composite literals

A struct is a fixed layout of named fields, and it is a **value**: assigning copies it, passing it copies it, storing it in a slice copies it. Section 3.5 is entirely about that.

```go
type Repository struct {
	Name         string   `yaml:"name"`
	Branch       string   `yaml:"branch,omitempty"`
	LocalDirName string   `yaml:"local_dir_name,omitempty"`
	Tags         []string `yaml:"tags,omitempty"`
}

type Project struct {
	Name         string       `yaml:"name"`
	Branch       string       `yaml:"branch"`
	Repositories []Repository `yaml:"repositories"`
}
```

Note `[]Repository` — a slice of *values*, laid out contiguously. Ten repositories is one allocation holding ten inlined structs; the Java `List<Repository>` is an array of ten pointers plus ten separate objects. That is where much of Go's performance comes from, and also where its copying semantics come from.

Build one with a composite literal, always with field names:

```go
ws := config.Workspace{
	Name:                 "test-ws",
	Path:                 tmp,
	CloneCommandTemplate: "echo clone {{.RepoName}} {{.DestDir}}",
	Projects: []config.Project{
		{
			Name:   "backend",
			Branch: "main",
			Repositories: []config.Repository{
				{Name: "api"},
				{Name: "auth", Branch: "dev"},
			},
		},
	},
}
```

Omitted fields take their zero value, so `{Name: "api"}` has an empty branch and a nil `Tags`. Inside a typed slice literal the element type is elided, so you write `{Name: "backend", …}`. The positional form `config.Repository{"api", "", "", nil}` is legal and you should never write it — it breaks silently when a field is inserted, and `go vet` complains for structs from other packages.

`&Config{…}` creates the struct and yields a pointer in one expression. Anonymous structs exist and are used mainly for table-driven tests, where a named type for one use would be noise.

## 3.5 Pointers, and when Go copies

Give this section your full attention. It is where Java experience actively misleads.

In Java every variable of a class type is a reference: `Repository r2 = r1;` makes both names point at one object. There is no other option. In Go, `r2 := r1` makes a **complete copy** — two independent structs, and `r2.Branch = "dev"` does not touch `r1`.

Copying happens on assignment, on passing an argument, on returning a value, on storing into or reading out of a slice, map or channel, and **on each iteration of `for _, x := range someSlice`**. That last one is the classic trap:

```go
// BROKEN: does nothing.
for _, ws := range cfg.Workspaces {
	if ws.Structure == "" {
		ws.Structure = config.StructureTree
	}
}
```

`ws` is a fresh copy of each element. You set a field on the copy, the loop iterates, the copy is discarded. `cfg.Workspaces` is untouched, the compiler is happy, there is no warning, and in Java this loop would have worked. Fix it by indexing into the original, or by taking a pointer to the element — which is exactly what `config.DefaultWorkspace` does, and the reason it loops with an index is precisely so it can return a pointer into the caller's config rather than a copy:

```go
func DefaultWorkspace(cfg *Config) (*Workspace, error) {
	for i := range cfg.Workspaces {
		if cfg.Workspaces[i].Default {
			return &cfg.Workspaces[i], nil
		}
	}
	…
}
```

Written as `for _, ws := range cfg.Workspaces { return &ws, nil }` it would compile and return a pointer to the loop's private copy — a value the caller can mutate with no effect on the config. The type system will not catch that for you.

A pointer is `*T`, taken with `&`. **There is no `->`**: Go dereferences automatically for field access and method calls, so `cfg.Editor` works whether `cfg` is a `Config` or a `*Config`. You write `*cfg` only when you want the whole value, as in `return []config.Workspace{*ws}, nil`, which copies the pointed-to workspace into a new slice.

There is no pointer arithmetic and no way to get a dangling pointer: the garbage collector keeps anything a pointer refers to alive, including a local whose address you returned. Escape analysis decides stack versus heap and you never think about it.

Use a pointer when the callee must mutate the caller's value (`ApplyEnvOverrides(cfg *Config)` exists to write into it); when nil is a meaningful state (`*Workspace` can be "none found", `Workspace` cannot); and **when the type carries a mutex or other non-copyable state** — `*Reporter`, always, because copying a struct containing a `sync.Mutex` gives you two locks protecting one logical resource. `go vet` catches the obvious cases with "passes lock by value"; take it seriously.

Pass by value for small structs the callee only reads. grazhda passes `config.Workspace`, `config.Project`, `config.Repository` and `RunOptions` around by value everywhere:

```go
func RepoPath(ws config.Workspace, proj config.Project, repo config.Repository) string
```

That signature promises, in the type system, that calling it cannot modify your workspace. Java cannot make that promise about any object parameter.

## 3.6 Methods and receivers

A method is a function with a receiver declared before its name:

```go
func (r *Reporter) SetTotal(n int) {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.total = n
	r.done = 0
}

func (e OsExecutor) Run(dir, command string) error {
	return e.RunContext(context.Background(), dir, command)
}
```

`r` and `e` are the equivalent of `this`, but named by you and declared explicitly. Convention is one or two letters, and consistency within a type matters more than the letter. Methods live at package level in any file of the package — there is no class body — and can be attached to any named type you declared here, including non-struct types such as `type BranchReader func(path string) (string, error)`.

**Value receiver versus pointer receiver is a real decision.** A value receiver gets a copy, so `func (r Reporter) SetQuiet() { r.Quiet = true }` silently modifies nothing. A pointer receiver gets the address and can mutate. Rule of thumb: if any method of a type needs a pointer receiver, give them all pointer receivers. Use value receivers for small immutable types, as `reporter.ExitError` does:

```go
type ExitError struct{ Code int }

func (e ExitError) Error() string { return fmt.Sprintf("exit code %d", e.Code) }
```

Go calls methods on addressable values automatically — if `r` is a `Reporter` variable, `r.SetTotal(3)` compiles because the compiler rewrites it as `(&r).SetTotal(3)`. That makes the distinction easy to forget, right up until interfaces are involved.

## 3.7 Multiple return values

A function returns any number of values, and the overwhelmingly common shape is `(result, error)`:

```go
func Load(path string) (*Config, error)
func RenderCloneCmd(tmpl string, proj Project, repo Repository, dest string) (string, error)
```

Callers destructure with `:=`. `_` is the blank identifier, for a value you must syntactically receive but do not want:

```go
ws, _ := makeWorkspace(t)
if _, err := os.Stat(repoPath); err == nil {
	// the path exists
}
```

That second line is a very common Go shape: call something for its error only. Return values can be named, which enables a bare `return`; grazhda mostly does not, and neither should you at first — named returns make it easy to lose track of what is actually returned.

## 3.8 Interfaces, satisfied implicitly

This is the idea that changes how you design.

An interface is a set of method signatures. A type satisfies it by having those methods. There is no `implements` clause — the type does not know the interface exists, the interface does not know the type exists, and the compiler checks at the point of assignment.

```go
type Executor interface {
	Run(dir, command string) error
	RunContext(ctx context.Context, dir, command string) error
	RunCapture(dir, command string) (string, error)
	RunCaptureContext(ctx context.Context, dir, command string) (string, error)
	RunInteractive(ctx context.Context, dir, command string) error
}

type OsExecutor struct{}

func (e OsExecutor) Run(dir, command string) error { … }
// … and the rest
```

`OsExecutor` never mentions `Executor`. It just happens to have the right methods.

Reverse the Java picture and the consequence appears. In Java the interface is defined next to the implementation, in the provider's package — `java.util.List` ships with `ArrayList`, a Spring service defines `FooService` and `FooServiceImpl` side by side — so consumers depend on the provider's package to name the interface. In Go, **the interface belongs to the consumer**: the package that needs a behaviour declares its shape, and any type with those methods qualifies, including one written afterwards in a package the interface's author never heard of. You can retrofit an abstraction onto code you do not own. In Java you would need an adapter class.

Interfaces should be small. `io.Writer`, the most-used interface in Go, has one method, and every file, socket, buffer, `strings.Builder` and `os.Stdout` satisfies it. Five methods, as `Executor` has, is at the upper end of comfortable; past that you are probably describing an object rather than a behaviour.

**The compile-time assertion idiom.** Because satisfaction is implicit, nothing tells you at the definition site that the method set is right — you find out at the first assignment, possibly in another package. So Go code states the intent with a discarded declaration:

```go
var _ Executor = OsExecutor{}
var _ Executor = (*MockExecutor)(nil)
```

Neither line allocates or runs anything, and both fail to compile if the type stops satisfying the interface. Put one next to every implementation you intend to be substitutable.

**The method-set gotcha those lines quietly demonstrate.** `OsExecutor`'s methods have value receivers, so both `OsExecutor` and `*OsExecutor` satisfy `Executor`. `MockExecutor`'s have pointer receivers, so **only `*MockExecutor` does**, and `var _ Executor = MockExecutor{}` fails with:

```
cannot use MockExecutor{} (value of struct type MockExecutor) as Executor value:
	MockExecutor does not implement Executor (method Run has pointer receiver)
```

That is why every test writes `mock := &executor.MockExecutor{}`. The reason is sound — taking the address of an arbitrary value is not always possible — but this is the error Go newcomers most often stare at, and now you know what it means the first time.

**An interface holding a nil pointer is not nil.** `var e *MyError = nil; var err error = e` gives an `err` for which `err == nil` is false, because the interface value has both a type and a value. The rule that avoids it entirely: **always declare error return types as `error`, never as a concrete error type.**

**The empty interface** `interface{}` has no methods, so everything satisfies it; since Go 1.18 write it as `any`. `ZgardConfig` uses `map[string]any` for a free-form YAML block. To get a concrete value out, use a type assertion with the comma-ok form (`val, ok := cur.(map[string]any)`, which yields false rather than panicking) or a type switch, which is `instanceof` chains done properly:

```go
switch v := cur.(type) {
case map[string]any:
	val, ok := v[part]
	if !ok {
		return nil, fmt.Errorf("%w: key %q not found", ErrKeyNotFound, fullKey)
	}
	return traversePath(val, rest, fullKey)
case []any:
	idx, err := strconv.Atoi(part)
	…
default:
	return nil, fmt.Errorf("cannot traverse into %T at segment %q", cur, part)
}
```

Inside each case `v` has that case's type. `%T` prints the dynamic type and is invaluable in exactly these messages.

## 3.9 Embedding instead of inheritance

Declare a field with a type and no name and its fields and methods are promoted:

```go
type SearchOptions struct {
	InspectOptions        // embedded
	Pattern string
	Glob    bool
	Regex   bool
}
```

Now `opts.Verbose` works on a `SearchOptions`, as does `opts.Ctx()`, the method declared on `InspectOptions`. It looks like `extends`. It is not, in three ways that matter.

**There is no subtype relationship.** A `SearchOptions` is not usable where an `InspectOptions` is expected; you say `opts.InspectOptions`, since the field's name is its type name.

**There is no virtual dispatch.** If `InspectOptions` had a `Describe()` that called `Ctx()`, and `SearchOptions` also declared `Ctx()`, the inherited `Describe()` would still call `InspectOptions.Ctx` — the embedded type cannot dispatch back into the outer one. There is no template-method pattern in Go. This is the difference people take longest to absorb, because everything else about embedding looks familiar.

**Shadowing is silent and legal.** Declare `Verbose` on the outer type too and `opts.Verbose` means the outer one, with the inner still reachable as `opts.InspectOptions.Verbose`. No `@Override`, no warning.

Embedding an *interface* is idiomatic, and grazhda's gRPC server depends on it:

```go
type Server struct {
	dukhpb.UnimplementedDukhServiceServer

	grpcServer atomic.Pointer[grpc.Server]
	monitor    *Monitor
	logger     *log.Logger
}
```

`UnimplementedDukhServiceServer` is generated code providing a stub for every RPC. Embedding it makes `Server` satisfy the full service interface immediately, so you override only what you have written, and adding an RPC to the `.proto` does not break existing servers. That is a deliberate compatibility mechanism built entirely out of embedding.

Otherwise prefer a named field. `Reporter` has `out io.Writer`, not an embedded one, because `rep.out` is clearer than promoting `Write` onto `Reporter`. Embed when you genuinely want the outer type to *be* the inner one's interface.

## 3.10 Arrays, slices, and the aliasing trap

An array has a fixed length that is part of its type — `[3]string` and `[4]string` are different types — and copies wholesale. You will almost never declare one.

A slice is the type you actually use: `[]string`, written like a Java `List`, implemented as a three-word header (pointer to a backing array, length, capacity) that is itself a value.

```go
var tags []string                            // nil: len 0, cap 0, no array
names := make([]string, len(repos))          // len 3, three empty strings
buf   := make([]string, 0, len(proj.Tags))   // len 0, cap 3 — preallocated
```

`append` returns a slice and **you must use the return value** — `errs = append(errs, "oops")`, never a bare `append(...)`, which is a compile error. The reason is the trap: if the backing array has spare capacity, `append` writes in place and returns a longer view of the same array; if not, it allocates, copies, and returns a slice pointing somewhere new. You cannot tell which happened.

Now the aliasing trap proper. Slicing does not copy:

```go
all := []string{"api", "auth", "web"}
first := all[:2]
first[0] = "CHANGED"
fmt.Println(all)         // [CHANGED auth web]
```

And it gets sharper, because `append` on a slice with spare capacity mutates memory beyond its own length:

```go
a := []string{"api", "auth", "web"}
b := a[:1]               // len 1, cap 3
b = append(b, "GHOST")   // writes into a[1]
fmt.Println(a)           // [api GHOST web]
```

This is the source of genuinely mysterious bugs. The defence is `copy` when you mean a copy, and the three-index slice `a[:1:1]` when you want to cap capacity and force the next `append` to allocate.

grazhda takes the defence seriously at every boundary that hands a slice to a caller. `Reporter.Results` and `Monitor.Snapshot` both do this:

```go
func (r *Reporter) Results() []OpResult {
	r.mu.Lock()
	defer r.mu.Unlock()
	out := make([]OpResult, len(r.results))
	copy(out, r.results)
	return out
}
```

Without the copy, a caller could write into the reporter's internal state, from another goroutine, past the mutex. Note the honest limitation: this is a *shallow* copy — each `OpResult`'s own `OutputLines []string` still points at the same array. For grazhda that is fine because those are never mutated after recording, and being able to say why is the point.

Passing a slice to a function passes the header by value: the callee cannot change your length, but it can absolutely change your elements.

## 3.11 Maps and comma-ok

`map[K]V` is a hash table. Keys must be comparable — no slices, maps or functions as keys; structs are fine if all their fields are comparable.

**Reading a missing key returns the zero value**, not an error and not null. The duplicate-detection loop in `config.Validate` relies on it:

```go
seenWS := make(map[string]bool, len(cfg.Workspaces))
for i, ws := range cfg.Workspaces {
	switch {
	case ws.Name == "":
		errs = append(errs, fmt.Sprintf("workspace[%d].name: required field missing", i))
	case seenWS[ws.Name]:
		errs = append(errs, fmt.Sprintf("workspace names must be unique: duplicate name %q", ws.Name))
	default:
		seenWS[ws.Name] = true
	}
}
```

No `containsKey` anywhere: `seenWS[ws.Name]` on a first sighting is `false`. When you must distinguish "absent" from "present with the zero value", use comma-ok: `val, ok := v[part]`. Delete with the builtin `delete(m, key)`; length with `len(m)`.

**The nil map, which is the failure worth showing.** A declared-but-not-made map is nil. Reading is safe; writing panics:

```go
var m map[string]bool
fmt.Println(m["x"])   // false — fine
m["x"] = true         // panic: assignment to entry in nil map
```

There is no lazy initialisation. Memorise the asymmetry: **nil slices accept `append`; nil maps do not accept writes.** Any struct field of map type needs an explicit `make` before first write, which is a real reason to write a `New…` function.

Maps are reference-like — the callee's writes are visible to you — and they are **not** safe for concurrent use. Concurrent writes crash the program with `fatal error: concurrent map writes`, which is not a recoverable panic. Guard with a mutex, or use `sync.Map` for the specific case of many readers and disjoint writers.

## 3.12 Errors are values

There is no `throw`, no `catch`, no unwinding. `error` is an ordinary interface with one method, `Error() string`. A function that can fail returns one last, and the caller checks it.

You will write `if err != nil` thousands of times. Two things reconcile you to it. First, error handling is *in the reading path*: a Java method that declares no checked exceptions can still throw six kinds of unchecked exception from four frames down with nothing at the call site saying so, whereas in Go every failure point is a visible `err` and every place you chose not to handle something is a visible `_`. Second, errors are values, so they compose with ordinary code — you can put one in a struct field, collect them in a slice, count them. `libs/reporter` does exactly this: a failed repository does not abort the run, its error goes into an `OpResult`, and the run continues. Expressing "continue on failure but remember" with exceptions requires a try/catch inside a loop and a hand-maintained list.

**Creating and wrapping.** `errors.New` for a fixed message, `fmt.Errorf` for a formatted one. `fmt.Errorf` with the `%w` verb produces an error that *contains* the original — Go's answer to exception chaining, opt-in per call site. Since Go 1.20 you can wrap more than one, which `config.Load` uses to keep both a sentinel and the underlying OS error:

```go
func Load(path string) (*Config, error) {
	data, err := os.ReadFile(path)
	if err != nil {
		if os.IsNotExist(err) {
			return nil, fmt.Errorf("%w: %s: %w", ErrNotFound, path, err)
		}
		return nil, fmt.Errorf("config file %q: %w", path, err)
	}
	var cfg Config
	if err := yaml.Unmarshal(data, &cfg); err != nil {
		return nil, fmt.Errorf("parsing config %q: %w", path, err)
	}
	return &cfg, nil
}
```

Use `%w` when a caller might reasonably test for the wrapped error and `%v` when you are deliberately hiding it. Wrapping is part of your API surface.

**Sentinel errors** are package-level values callers compare against, named `Err…`:

```go
var (
	ErrNoWorkspace   = errors.New("no matching workspace")
	ErrNoProject     = errors.New("no matching project")
	ErrFilterInvalid = errors.New("invalid filter combination")
	ErrCancelled     = errors.New("operation cancelled")
)

return nil, fmt.Errorf("%w: workspace %q not found in config", ErrNoWorkspace, name)
```

**`errors.Is`** walks the wrap chain. Never compare with `==`, because what you get back is a wrapper:

```go
if errors.Is(err, workspace.ErrNoProject) { … }
```

That is Java's `catch (NoSuchProjectException e)`, decided by the caller rather than by a type hierarchy.

**Custom error types** carry structured data. `config.ValidationError` collects every message from one validation pass, and implementing `Unwrap` is what puts it into the chain `errors.Is` walks:

```go
type ValidationError struct {
	Errs []string
}

func (e *ValidationError) Error() string {
	return "configuration is invalid: " + strings.Join(e.Errs, "; ")
}

// Unwrap lets errors.Is(err, ErrInvalid) succeed.
func (e *ValidationError) Unwrap() error { return ErrInvalid }
```

So a caller who only wants to know "is the config bad" writes `errors.Is(err, config.ErrInvalid)` without knowing the type exists, while a caller who wants the list uses **`errors.As`**, which finds an error of a given type in the chain and assigns it through a pointer you supply. `zgard`'s root command uses it to turn partial failure into an exit code:

```go
if err := rootCmd.ExecuteContext(ctx); err != nil {
	var exitErr reporter.ExitError
	if errors.As(err, &exitErr) {
		os.Exit(exitErr.Code)
	}
	fmt.Fprintln(os.Stderr, clr.Red(err.Error()))
	os.Exit(1)
}
```

Match the receiver you declared: `ExitError` has a value receiver so the target is an `ExitError` variable, while `ValidationError`'s methods have pointer receivers, so you declare `var vErr *config.ValidationError` and pass `&vErr`.

**Not everything negative is an error.** `Validate` returns `[]string`, not `error`, because a validation pass is not a failure of the function — it succeeded, and its answer is a list. The `error` is constructed later by whoever needs one. Resist making every negative outcome an `error`.

**Message style:** lowercase, no trailing punctuation, no "failed to" prefix, because messages get concatenated by wrapping into things like `loading config: parsing config "x.yaml": yaml: line 3: mapping values are not allowed`. If every layer said "Failed to", that would be unreadable.

## 3.13 `defer`, `panic`, `recover`

`defer` schedules a call to run when the surrounding **function** returns — not when the block ends — on every exit path, including a panic.

```go
func (r *Reporter) Record(res OpResult) {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.results = append(r.results, res)
	…
}
```

Lock, then immediately defer the unlock. Every `return` in the rest of the function unlocks correctly, and adding a new early return cannot introduce a leak. It is `try`/`finally` with the cleanup adjacent to the acquisition instead of thirty lines below.

Deferred calls run **last in, first out**, so resources are released in reverse order of acquisition and an inner resource closes before the outer one it depends on.

**Arguments are evaluated at `defer` time, not at call time.** `defer fmt.Println(time.Since(start))` prints roughly zero; wrapping it in a closure defers the evaluation too. Which leads to the cleanup-on-failure pattern grazhda uses in `lifecycle.go`, where a clone that fails halfway must not leave a partial directory behind:

```go
var success bool
defer func() {
	if !success {
		os.RemoveAll(repoPath) //nolint:errcheck
	}
}()

if err := exec.RunContext(opts.Ctx(), projPath, cmd); err != nil {
	rep.Record(reporter.OpResult{ … Err: err … })
	return
}

success = true
rep.Record(reporter.OpResult{ … Msg: fmt.Sprintf("cloned (%s)", branch) … })
```

Read the shape: declare a flag as `false`, register the rollback as a closure that reads the flag, do the work, set the flag on success. The closure captures the *variable*, not its value, so it sees whatever `success` holds at return time. Every path out of the function — the error return, a later panic, a return you add next month — cleans up, and you wrote the cleanup once, next to the thing it undoes. Learn this pattern by heart.

`defer` inside a loop is a common mistake, because it accumulates until the *function* ends; wrap the body in its own function if you need per-iteration cleanup.

**`panic` and `recover`.** A panic unwinds the stack running deferred functions and then crashes with a stack trace; `recover`, called inside a deferred function, stops the unwind. You will almost never write either. Panic is for programmer error and impossible states — index out of range, nil map write — not for conditions a caller might handle. A missing config file is `ErrNotFound`; malformed YAML is a wrapped error. The legitimate uses are narrow: a package initialiser where failure means the program cannot run, `MustCompile`-style helpers whose input is a source literal, and recovering at the top of a long-lived server goroutine so one bad request does not kill the process — which gRPC's interceptors already do for you. Do not use panic and recover to emulate exceptions; it reads as foreign to every Go developer who will read your code.

## 3.14 Strings, bytes and runes

A Go `string` is an immutable, read-only slice of bytes, conventionally UTF-8 — not UTF-16 like Java's, and not null-terminated.

```go
s := "✓ ok"
len(s)           // 6 — the check mark is three bytes
len([]rune(s))   // 4
s[0]             // a byte (uint8), not a character
```

`len` is the **byte** count. Ranging decodes runes, giving byte offsets and code points:

```go
for i, r := range "✓ ok" { … }   // 0 '✓', 3 ' ', 4 'o', 5 'k'
```

A `rune` is `int32`, a Unicode code point — the closest thing to Java's `char`, except Java's is 16 bits and needs surrogate pairs above the BMP. Conversions `[]byte(s)`, `string(b)` and `[]rune(s)` all copy. `string(someBytes)` is how you turn command output into text:

```go
out, err := exec.Command("git", "-C", path, "symbolic-ref", "--short", "HEAD").Output()
if err != nil {
	return "", err
}
return strings.TrimSpace(string(out)), nil
```

Beware `string(65)`, which is `"A"` — an integer-to-rune conversion, not `"65"`. Use `strconv.Itoa` for that.

Concatenating in a loop with `+=` is quadratic. Use `strings.Builder`, which satisfies `io.Writer` and therefore drops into anything that takes one — exactly how grazhda's tests capture reporter output:

```go
var out, errOut strings.Builder
rep := reporter.New(&out, &errOut)
…
if !strings.Contains(out.String(), "already exists, skipped") { … }
```

`bytes.Buffer` is the mutable byte equivalent, used in `RenderCloneCmd` to receive a rendered template.

The `strings` package is your `String` methods and `StringUtils` combined — `Contains`, `HasPrefix`, `TrimSuffix`, `Split`, `Join`, `LastIndex`, `TrimSpace` — all package functions, because `string` is a builtin with no method set:

```go
func LastSegment(name string) string {
	name = strings.TrimSuffix(name, ".git")
	if idx := strings.LastIndex(name, "/"); idx >= 0 {
		return name[idx+1:]
	}
	return name
}
```

`name[idx+1:]` slices a string without copying, which is safe because strings are immutable.

Formatting verbs worth memorising: `%s` string, `%d` integer, `%q` a quoted and escaped string (excellent in error messages), `%v` default, `%+v` a struct with field names, `%T` dynamic type, `%w` an error to wrap.

## 3.15 Struct tags and reflection

The backtick strings after struct fields are **struct tags** — an arbitrary string stored in the type's metadata and readable at runtime through `reflect`.

```go
type Workspace struct {
	Name      string    `yaml:"name"`
	Path      string    `yaml:"path"`
	Structure string    `yaml:"structure,omitempty"`
	Projects  []Project `yaml:"projects"`
}
```

They are inert. The compiler checks nothing beyond basic syntax, so if you typo `yam:"name"` the code compiles and the field silently never populates. `go vet` catches malformed tags but not misspelled keys — treat a field that mysteriously stays at its zero value after decoding as a tag typo until proven otherwise.

The decoder gives them meaning. `yaml.Unmarshal` reflects over the target, reads each `yaml` tag, and matches document keys:

```go
var cfg Config
if err := yaml.Unmarshal(data, &cfg); err != nil { … }
```

Note `&cfg` — the decoder needs a pointer to write through; passing `cfg` gives you a silently empty config. `,omitempty` applies on the way out, dropping zero-valued fields when marshalling. And **only exported fields are visible to reflection**, which is the other half of why `Reporter`'s `out` and `mu` are lower-case and a config struct's fields are all capitalised.

This is Jackson's `@JsonProperty` minus the annotation type system, minus compile-time checking, minus the processor: strictly weaker and considerably simpler. The same mechanism drives `encoding/json`, database row scanners, and CLI flag binders.

`ApplyEnvOverrides` shows the layering grazhda uses on top — decode the file, then overlay environment variables explicitly, in code, with no reflection:

```go
func ApplyEnvOverrides(cfg *Config) {
	if cfg == nil {
		return
	}
	if v := os.Getenv(EnvEditor); v != "" {
		cfg.Editor = v
	}
	if v := os.Getenv(EnvDukhPort); v != "" {
		if p, err := strconv.Atoi(v); err == nil {
			cfg.Dukh.Port = p
		}
	}
}
```

Twelve boring lines instead of a `@ConfigurationProperties` binder. Which is better depends on how much you value reading the precedence rules without consulting a framework's documentation.

## 3.16 Generics, briefly

Type parameters arrived in Go 1.18. Constraints are interfaces used as type sets: `any` allows anything, `comparable` allows `==`, and the standard library ships generic `slices` and `maps` packages plus `atomic.Pointer[T]`, which grazhda's daemon does use.

```go
func Map[T, U any](in []T, f func(T) U) []U {
	out := make([]U, 0, len(in))
	for _, v := range in {
		out = append(out, f(v))
	}
	return out
}
```

grazhda has essentially no generic code of its own, and that is normal. The domain is concrete — `Resolve(reg *Registry, names []string) ([]Package, error)` is about packages, not about a `T`, and there is no second element type waiting to reuse the topological sort. Interfaces already cover the polymorphism that matters: `Executor` abstracts behaviour, whereas a type parameter would abstract *shape*, which is not the axis grazhda varies along. And Go generics do not allow methods with their own type parameters, so the community default remains "write the concrete version, generalise on the third occurrence."

Coming from Java the absence feels like a hole. In practice it barely bites: slices and maps are built into the language and already type-safe, and those account for the large majority of what Java generics do day to day.

## 3.17 A few smaller things

**No implicit numeric conversion.** `var d time.Duration = someInt` does not compile; you write `time.Duration(opts.CloneDelaySeconds) * time.Second`. Untyped constants are the exception, which is why `5 * time.Second` is fine. Typed values never convert silently, not even `int32` to `int64`.

**`switch` does not fall through**, so no `break` is needed, and a `switch` with no expression is a condition chain that reads far better than `if`/`else if`:

```go
switch {
case res.Err != nil:
	symbol = clr.Red(SymbolFailed)
case res.Skipped:
	symbol = clr.Yellow(SymbolSkipped)
default:
	displayMsg = clr.Green(displayMsg)
}
```

**`for` in its shapes:**

```go
for i := 0; i < n; i++ { }      // C-style
for len(queue) > 0 { }          // while
for { }                         // forever
for i, repo := range repos { }  // index and copy of the value
for i := range repos { }        // index only
for k, v := range someMap { }   // key and value
for range 10 { }                // Go 1.22+
```

**Functions are values, and closures capture variables.** A named function type is Go's `@FunctionalInterface` without the ceremony:

```go
type BranchReader func(path string) (string, error)

func NewMonitor(configPath string, logger *log.Logger, reader BranchReader) *Monitor {
	if reader == nil {
		reader = GitBranchReader
	}
	…
}
```

`RunOverRepos` does the same for the per-repository work: `fn func(proj config.Project, projPath string, repo config.Repository)`.

**`init()`** runs at package load, before `main`; a package can have several. `zgard`'s `root.go` uses one to register persistent flags. Use it sparingly — it is invisible control flow, and it is the one place Go has something like a static initialiser block.

# Part 4 — Concurrency

## 4.1 Goroutines are cheap

`go f()` runs `f` concurrently and returns immediately. That is the whole syntax.

A goroutine is not an OS thread. It starts with a couple of kilobytes of stack that grows and shrinks on demand, and the runtime multiplexes many goroutines onto a few OS threads, switching at blocking points. Hold onto the numbers: a Java thread costs around a megabyte of stack and a kernel-visible thread, so a few thousand is a lot; a million goroutines in one process is unremarkable. `zgard ws pull --parallel` across five hundred repositories launches five hundred goroutines with no pool, no executor service and no thread-count tuning parameter. Goroutine count is not the scarce resource.

Two rules follow from goroutines being cheap and unsupervised. **Nothing waits for one unless you make it** — when `main` returns the process exits and every running goroutine is killed mid-statement; there is no `join` and no non-daemon-thread semantics keeping things alive. And **a goroutine that leaks leaks forever** — one blocked on a channel nobody will send to is never collected, so always know how each goroutine you start will end.

## 4.2 The anonymous goroutine and the loop variable

The common form is a closure launched immediately. This is `libs/workspace/fanout.go`, essentially verbatim:

```go
var wg sync.WaitGroup
for _, proj := range ws.Projects {
	for _, repo := range proj.Repositories {
		wg.Add(1)
		go func() {
			defer wg.Done()
			fn(proj, projPath, repo)
		}()
	}
}
wg.Wait()
```

It also contains the most famous bug in Go's history — or rather, it used to. Before Go 1.22, `proj` and `repo` were declared **once per loop**, not once per iteration. Every goroutine closed over the same two variables, and by the time they actually ran the loop had usually finished and both held the last element. Three repositories, three goroutines, all operating on the third one — sometimes, depending on scheduling, with no warning.

The workaround was the redeclaration idiom, which you can still see in the real `fanout.go`:

```go
for _, proj := range ws.Projects {
	proj := proj            // shadow: a new variable per iteration
	for _, repo := range proj.Repositories {
		repo := repo
		…
	}
}
```

`proj := proj` declares a new `proj` in the loop body's scope, and the closure captures *that*. It looks like a no-op and is anything but.

**Go 1.22 changed the language**: loop variables are now scoped per iteration, so the naive version is correct. Those `proj := proj` lines are harmless leftovers, since the module declares `go 1.26.1`. You still need to know this, because any code or blog post written before 2024 assumes the old rule, and because the behaviour is selected by the `go` directive in `go.mod` — a module declaring `go 1.21` still gets the old semantics on a new toolchain.

The other way to pass a value in is as an argument, which was always correct: `go func(p config.Project) { … }(proj)`. Arguments are evaluated at `go` time, so values are snapshotted.

## 4.3 `sync.WaitGroup`

A counter with a wait: `Add(n)` before starting, `Done()` when finished, `Wait()` blocks until zero. Three rules cover every mistake people make with it. **`Add` before `go`, never inside the goroutine** — otherwise `Wait` can observe zero before the goroutine is scheduled. **`Done` in a `defer`, as the goroutine's first statement**, so a panic or early return still decrements. **Never copy a `WaitGroup`**; pass `*sync.WaitGroup` if it must cross a function boundary, and `go vet` will catch you.

A `WaitGroup` gives you the join and nothing else — no return values, no error propagation, no cancellation. That is why `RunOverRepos` records outcomes into a shared `*reporter.Reporter` rather than collecting them from the goroutines: the reporter is the concurrency-safe accumulator and the WaitGroup only answers "are they all done." When you need errors out of a parallel fan-out, `golang.org/x/sync/errgroup` is the standard next step. Since Go 1.25 there is also `wg.Go(f)`, which does the `Add` and `defer Done` pairing for you.

## 4.4 `sync.Mutex` and `sync.RWMutex`

`sync.Mutex`'s zero value is unlocked and ready — no constructor, no `new ReentrantLock()` — and crucially **it is not reentrant**. A goroutine that locks a mutex it already holds deadlocks instantly. Java's `synchronized` is reentrant; this is a real behavioural difference and it catches people who factor a locked method into two locked methods.

The idiom is always lock-then-defer-unlock, and what is protected is the fields declared directly beneath `mu` in the struct. That grouping is a convention worth following, because Go has no syntax tying a lock to the data it guards:

```go
type Reporter struct {
	out    io.Writer
	errOut io.Writer

	mu      sync.Mutex   // guards everything below
	results []OpResult
	total   int
	done    int
}
```

The mutex is a value field, which is why `Reporter` must always be used as `*Reporter` and why `reporter.New` returns a pointer.

`sync.RWMutex` distinguishes readers from writers: any number of concurrent `RLock` holders, or one exclusive `Lock`. Use it when reads dominate, which is exactly the daemon monitor's situation — one goroutine writes a snapshot every few minutes and every gRPC `Status` call reads it:

```go
func (m *Monitor) Snapshot() []WorkspaceHealth {
	m.mu.RLock()
	defer m.mu.RUnlock()
	cp := make([]WorkspaceHealth, len(m.snapshot))
	copy(cp, m.snapshot)
	return cp
}

func (m *Monitor) scan() {
	… // all the filesystem and git work, building `result`, outside the lock
	m.mu.Lock()
	m.snapshot = result
	m.mu.Unlock()
	m.logger.Info("monitor: scan complete", "workspaces", len(result))
}
```

Two details in `scan` worth copying: the whole scan happens *outside* the lock, which is held only for the pointer swap; and the logging happens after the unlock, because logging can block on I/O and you never hold a lock across I/O. Compute unlocked, swap locked — that is how you keep an RWMutex from serialising your program. And `Snapshot` returns a copy, for the reasons in 3.10.

There is also `sync/atomic` for single values, which the daemon's `Server` uses where a mutex would be overkill: `grpcServer atomic.Pointer[grpc.Server]` and `stopped atomic.Bool`. The real source explains the need precisely — `Serve` stores the server and `GracefulStop` reads it, and those can run on different goroutines because a signal or a `Stop` RPC can arrive during startup.

## 4.5 Channels

A channel is a typed, synchronised pipe.

```go
ch := make(chan string)      // unbuffered
buf := make(chan string, 10) // buffered
ch <- "value"                // send
v := <-ch                    // receive
close(ch)                    // further sends panic; receives drain then return zero
```

An unbuffered channel is a **rendezvous**: the sender blocks until a receiver is ready and vice versa, and that synchronisation is often the point rather than a side effect. Receiving from a closed channel returns immediately with the zero value; `v, ok := <-ch` distinguishes. `for v := range ch` receives until close. Channel directions can be part of a type — `chan<- int` send-only, `<-chan int` receive-only — and are worth using in signatures to document intent.

grazhda's monitor uses three channels, each showing a different pattern:

```go
type Monitor struct {
	…
	stopCh chan struct{}
	doneCh chan struct{}

	// A nil reply means fire-and-forget. A non-nil reply channel is closed by
	// the loop once the scan it requested completes.
	triggerScan chan chan struct{}
}
```

**`chan struct{}` as a pure signal.** `struct{}` is the empty struct: zero bytes, no data. A channel of it carries only the *event* of a send or a close:

```go
func (m *Monitor) Stop() {
	close(m.stopCh)
	<-m.doneCh
}
```

`close` unblocks every receiver at once, permanently — a broadcast you cannot do with a send. Then `<-m.doneCh` blocks until the loop's `defer close(m.doneCh)` fires, which is a join. Two statements, and `Stop` returns only once the loop has stopped and finished any in-flight scan.

**`chan chan struct{}` as request/reply.** The caller creates a reply channel, sends it, and waits for it to close — a synchronous call built from asynchronous primitives:

```go
func (m *Monitor) TriggerScanAndWait(ctx context.Context) error {
	reply := make(chan struct{})
	select {
	case m.triggerScan <- reply:
	case <-ctx.Done():
		return ctx.Err()
	}
	select {
	case <-reply:
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}
```

Channels are not always the answer. Go's own advice: use channels to pass ownership or to signal, use a mutex to protect shared state. The reporter's accumulator is a mutex because a hundred goroutines appending to a list is exactly what mutexes are for; the monitor's control flow is channels because it is coordination.

## 4.6 `select`

`select` waits on several channel operations and takes whichever is ready, picking pseudo-randomly among several to prevent starvation. This is the heart of the daemon:

```go
select {
case <-timer.C:
	m.scan()

case reply := <-m.triggerScan:
	timer.Stop()
	m.logger.Info("monitor: manual scan triggered")
	m.scan()
	if reply != nil {
		close(reply)
	}

case <-m.stopCh:
	timer.Stop()
	m.logger.Info("monitor: stopping")
	return
}
```

A `default` case makes `select` non-blocking, which is how `TriggerScan` drops a redundant signal rather than queueing a second one:

```go
func (m *Monitor) TriggerScan() {
	select {
	case m.triggerScan <- nil: // nil reply = fire-and-forget
	default:
	}
}
```

If the buffered channel (capacity 1) is full, a scan is already pending and a second would be redundant — coalescing duplicate requests in five lines, with no queue and no flag.

A `select` with no ready case and no `default` blocks forever, and the runtime detects the whole-program case with `fatal error: all goroutines are asleep - deadlock!`.

## 4.7 `time.Timer` versus `time.Ticker`

A `Ticker` fires repeatedly on a fixed interval; a `Timer` fires once. `for range ticker.C { work() }` is the shorter code, and the monitor deliberately does not use it:

```go
func (m *Monitor) loop() {
	defer close(m.doneCh)
	m.scan()

	for {
		period := m.loadPeriod()
		timer := time.NewTimer(period)
		select {
		case <-timer.C:
			m.scan()
		case reply := <-m.triggerScan:
			timer.Stop()
			…
		case <-m.stopCh:
			timer.Stop()
			return
		}
	}
}
```

Two requirements force the Timer. **The period is re-read from configuration before every wait** — a Ticker's interval is fixed at construction, whereas `m.loadPeriod()` re-loads the config each iteration, so editing `dukh.monitoring.period_mins` takes effect at the next tick with no restart. And **a manual trigger must interrupt the wait and reset the schedule**: with a Ticker, a manual scan at minute 4 would still be followed by the automatic tick at minute 5, whereas here the trigger case stops the timer and the next one starts from now.

There is also a robustness argument: a Ticker whose consumer is slower than its period silently drops ticks, since its channel has capacity 1, while a timer recreated after each unit of work cannot fall behind. `timer.Stop()` in the non-firing branches releases it promptly; on Go 1.23 and later timers are collected even without `Stop` and no draining is required, but calling it stays correct and clear. For a fixed-rate heartbeat, use a Ticker; for anything whose schedule can change, a Timer.

## 4.8 `context.Context`

`Context` carries cancellation, deadlines and request-scoped values across API boundaries. Java has no direct equivalent; the closest is a cancellable `Future` plus a thread-local, glued together.

```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
```

`ctx.Done()` is a channel closed when the context is cancelled or expires, and `ctx.Err()` says which. **Always `defer cancel()`**, even on a timeout context — not calling it leaks the timer and the watching goroutine, and `go vet` flags the omission.

**The convention: `Context` is the first parameter, always named `ctx`, never stored in a struct.** grazhda breaks the last part deliberately, and it is worth seeing why:

```go
type RunOptions struct {
	Context context.Context // nil means context.Background()
	DryRun  bool
	…
}

func (o RunOptions) Ctx() context.Context { return ctxOr(o.Context) }
```

`RunOptions` *is* the per-invocation request object, it does not outlive the call, and threading a separate `ctx` through a dozen functions that already take `opts` would be noise. The `Ctx()` accessor makes the nil case safe so `RunOptions{}` stays a usable zero value. The discipline this requires is that a `RunOptions` value must never be cached or reused, or you have stored a stale context.

Cancellation gets honoured two ways. Through the standard library, where `exec.CommandContext` kills the child process when the context is done:

```go
func (e OsExecutor) RunContext(ctx context.Context, dir, command string) error {
	var stderr bytes.Buffer
	cmd := shellCommand(ctx, command)   // exec.CommandContext(ctx, "sh", "-c", command)
	cmd.Dir = dir
	cmd.Stderr = &stderr
	if err := cmd.Run(); err != nil {
		if ctx.Err() != nil {
			return fmt.Errorf("interrupted: %w", ctx.Err())
		}
		if msg := LastMeaningfulLine(stderr.String()); msg != "" {
			return fmt.Errorf("%s", msg)
		}
		return err
	}
	return nil
}
```

The `ctx.Err() != nil` check distinguishes "the command failed" from "we cancelled it", so Ctrl-C is not reported as a git error. And by polling at a safe point, which sequential fan-out does between repositories:

```go
if err := opts.Ctx().Err(); err != nil {
	return fmt.Errorf("%w: %w", ErrCancelled, err)
}
fn(proj, projPath, repo)
```

Cancelling between repositories rather than mid-clone is a design choice: a half-cloned repository is worse than one more completed clone.

Where does the context come from? For a CLI, from the signal handler — this is `zgard`'s entire Ctrl-C story:

```go
ctx, cancel := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer cancel()

if err := rootCmd.ExecuteContext(ctx); err != nil { … }
```

Every command below reaches it via `cmd.Context()`, so Ctrl-C propagates all the way down to killing a running `git clone`. For a gRPC server the framework hands each handler a context cancelled when the client disconnects. `context.TODO()` marks "a context belongs here and I have not wired it yet"; never pass `nil`.

## 4.9 The race detector

`-race` instruments every memory access and reports unsynchronised read/write pairs at runtime.

```bash
$ go test -race ./...
```

It costs roughly ten times the CPU, so it is a test and staging tool. It has **no false positives** — a report is a real data race — but it only reports races that actually occurred, so exercise the concurrent paths.

Here is a real one it would catch. Remove the mutex from `Reporter.Record`, leaving `r.results = append(r.results, res)` unguarded, and run `zgard ws pull --parallel`. `RunOverRepos` launches one goroutine per repository, each calling `Record` when its git command finishes, and several finish at once. Each reads the three-word slice header, appends, and writes a new one back. Two that interleave can both read length 4, both write into slot 4, and both store length 5 — one result silently lost. If the append reallocates, one goroutine can write into an array the other has already abandoned.

`go test -race` prints exactly this:

```
WARNING: DATA RACE
Write at 0x00c0000b4020 by goroutine 9:
  github.com/vhula/grazhda/libs/reporter.(*Reporter).Record()
      libs/reporter/reporter.go:117 +0x64

Previous write at 0x00c0000b4020 by goroutine 8:
  github.com/vhula/grazhda/libs/reporter.(*Reporter).Record()
      libs/reporter/reporter.go:117 +0x64
```

Two goroutines, the same line, the same address. Without `-race` the symptom is "the summary sometimes says 19 pulled when there were 20 repositories", observed once a month and never reproducible. The same instrument catches any read of `m.snapshot` from a gRPC handler not holding `RLock` while `scan` replaces it. Make `go test -race ./...` part of your standard test target.

# Part 5 — Testing

## 5.1 The shape of a test

Testing is in the standard library and the toolchain. There is no JUnit, no `@Test`, no runner to configure, and no assertion library in the default kit. Files named `*_test.go` are compiled only by `go test`, and a test is a function named `TestXxx` taking `*testing.T`:

```go
func TestInit_ClonesRepos(t *testing.T) {
	ws, _ := makeWorkspace(t)
	var out, errOut strings.Builder
	rep := reporter.New(&out, &errOut)
	mock := &executor.MockExecutor{}

	if err := workspace.Init(ws, mock, rep, workspace.RunOptions{}); err != nil {
		t.Fatalf("Init error: %v", err)
	}
	if len(mock.Calls) != 2 {
		t.Fatalf("expected 2 clone calls, got %d: %v", len(mock.Calls), mock.Calls)
	}
	if !strings.Contains(mock.Calls[0], "api") {
		t.Errorf("expected first call for 'api', got %q", mock.Calls[0])
	}
}
```

**`t.Errorf` marks the test failed and continues; `t.Fatalf` marks it failed and stops.** Use `Fatalf` when continuing would be meaningless and `Errorf` when you want several independent problems reported from one run. There is no `assertEquals`; you write the `if`. The message convention is `got X, want Y`, and `%q` earns its place because it makes empty and whitespace-only strings visible.

That file declares `package workspace_test`, not `package workspace`. Go allows a second package in the same directory with a `_test` suffix, which can only see the exported API — so the tests exercise `workspace.Init` exactly as the CLI does and cannot reach into helpers. Prefer this form; when you genuinely need to test an unexported function, put that test in `package workspace` in a separate file.

## 5.2 Running tests

```bash
$ go test ./...                    # every package in the module
$ go test -v ./libs/workspace
$ go test -run TestInit ./...      # regex filter on names, including subtests
$ go test -race ./...
$ go test -count=1 ./...           # defeat the result cache
$ go test -coverprofile=c.out ./... && go tool cover -html=c.out
```

Results are cached per package and invalidated by any change to the package, its dependencies or its environment; `(cached)` means nothing ran. Tests within a package run sequentially by default while different packages run in parallel, and `t.Parallel()` opts a test into running concurrently with its siblings.

## 5.3 Subtests and table-driven tests

`t.Run(name, func(t *testing.T))` creates a nested test with its own name and its own `Fatalf` scope. Once you have that, the natural next step is to put the cases in a slice and loop — the dominant Go testing idiom and the standard library's own style:

```go
func TestResolveDestName(t *testing.T) {
	tests := []struct {
		name         string
		repoName     string
		localDirName string
		structure    string
		want         string
	}{
		{"tree keeps full name", "org/pack/repo", "", config.StructureTree, "org/pack/repo"},
		{"list takes last segment", "org/pack/repo", "", config.StructureList, "repo"},
		{"list strips .git", "org/repo.git", "", config.StructureList, "repo"},
		{"explicit override wins", "org/pack/repo", "custom", config.StructureList, "custom"},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got := workspace.ResolveDestName(tt.repoName, tt.localDirName, tt.structure)
			if got != tt.want {
				t.Errorf("ResolveDestName(%q, %q, %q) = %q, want %q",
					tt.repoName, tt.localDirName, tt.structure, got, tt.want)
			}
		})
	}
}
```

The anonymous struct is declared inline because it has one use. Adding a case is one line, and every case gets its own name in the output, so a failure reads `TestResolveDestName/list_strips_.git` rather than "line 87". This is `@ParameterizedTest` without the annotations, the argument provider or the reflection. The pattern generalises to error cases with a `wantErr error` field checked by `errors.Is`.

Use a table when cases differ only in *data*. When they differ in *setup* — one pre-creates a directory, one configures a mock to fail on the third call — separate named functions read better, which is why `lifecycle_test.go` is a long list of `TestInit_SkipsExistingRepo`, `TestInit_DryRun_NoCallsNoFilesystemChanges`, `TestInit_ContinueOnFailure`. Do not force a table onto tests that are not tabular.

## 5.4 `t.TempDir`, `t.Setenv`, `t.Cleanup`, `t.Helper`

`t.TempDir()` creates a unique directory and registers its removal when the test ends, including on failure. No cleanup code, and no shared `/tmp` path to collide on when tests run in parallel:

```go
func TestPurge_RemovesDirectory(t *testing.T) {
	tmp := t.TempDir()
	wsDir := filepath.Join(tmp, "myws")
	if err := os.MkdirAll(wsDir, 0o755); err != nil {
		t.Fatal(err)
	}

	ws := config.Workspace{Name: "myws", Path: wsDir}
	var out, errOut strings.Builder
	rep := reporter.New(&out, &errOut)

	if err := workspace.Purge(ws, rep, workspace.RunOptions{NoConfirm: true}); err != nil {
		t.Fatalf("Purge error: %v", err)
	}
	if _, err := os.Stat(wsDir); !os.IsNotExist(err) {
		t.Error("expected directory to be removed")
	}
}
```

Every filesystem test in grazhda starts this way; the project's rules forbid touching a real home directory and this is the mechanism.

`t.Setenv(key, value)` sets an environment variable and restores it afterwards — the right way to test `ApplyEnvOverrides`. It marks the test non-parallel, because the process environment is global, and calling `t.Parallel()` in the same test panics: the toolchain protecting you from a race it cannot otherwise see.

`t.Cleanup(func())` registers arbitrary teardown, LIFO, on both success and failure. It is what `TempDir` and `Setenv` use internally, and it is better than `defer` in a helper, because a helper's `defer` fires when the *helper* returns.

A helper that calls `t.Fatal` should call `t.Helper()` first, so failures are attributed to the caller's line rather than the helper's:

```go
func makeWorkspace(t *testing.T) (config.Workspace, string) {
	t.Helper()
	tmp := t.TempDir()
	ws := config.Workspace{
		Name:                 "test-ws",
		Path:                 tmp,
		CloneCommandTemplate: "echo clone {{.RepoName}} {{.DestDir}}",
		Projects: []config.Project{{
			Name:   "backend",
			Branch: "main",
			Repositories: []config.Repository{{Name: "api"}, {Name: "auth", Branch: "dev"}},
		}},
	}
	return ws, tmp
}
```

That one fixture backs most of `lifecycle_test.go`. Passing `t` into helpers is the normal Go pattern, and it replaces `@BeforeEach` and injected fixtures with an ordinary function call you can see at the top of each test.

## 5.5 Golden output

The reporter's contract is its output format, so the tests assert on text. The simple form is substring matching against a captured `strings.Builder`:

```go
if !strings.Contains(out.String(), "[DRY RUN] would clone") {
	t.Errorf("expected dry-run clone preview, got: %q", out.String())
}
```

Substring assertions survive incidental changes — a colour code, an added counter — while pinning the part that is actually the contract. When the whole output *is* the contract, the golden-file pattern is better: store the expected output in `testdata/`, compare, and support a flag to regenerate.

```go
var update = flag.Bool("update", false, "rewrite golden files")

golden := filepath.Join("testdata", "status_table.golden")
if *update {
	os.WriteFile(golden, []byte(got), 0o644)
}
want, err := os.ReadFile(golden)
if err != nil {
	t.Fatal(err)
}
if got != string(want) {
	t.Errorf("output mismatch\n--- got ---\n%s\n--- want ---\n%s", got, want)
}
```

`go test ./... -update` regenerates and you review the diff in git like any other change. The directory name `testdata` is special: the Go tool ignores it when looking for packages.

## 5.6 Designing for testability: inject an interface

This is the most important section in Part 5, and the reason `libs/executor` exists.

grazhda's whole purpose is running `git clone`, `git pull`, `git stash`. The naive design has `workspace.Init` call `exec.Command("sh", "-c", cmd).Run()` directly, and every consequence of that is bad: tests would clone real repositories over the network, so they would be slow, flaky, offline-hostile and would create real directories; testing a *failure* would need a repository that reliably fails; testing "does init skip repositories that already exist" would need a real clone first; and testing dry-run would mean trusting that no command ran, with no way to check.

So the project makes shelling out a named dependency. The `Executor` interface from 3.8 lives in `libs/executor`, and every domain function takes one as a parameter:

```go
func Init(ws config.Workspace, exec executor.Executor, rep *reporter.Reporter, opts RunOptions) error
func Pull(ws config.Workspace, exec executor.Executor, rep *reporter.Reporter, opts RunOptions) error
```

No Spring, no `@Autowired`, no container, no component scan. **Dependency injection in Go is a function parameter.** The composition root is the Cobra command in `cli/`, which passes `executor.OsExecutor{}` — an empty struct with no state, which is a perfectly normal Go type that exists only to carry a method set. `OsExecutor` is the *only* place in the codebase that touches `os/exec`.

The fake is hand-written, forty lines, and lives next to the real one:

```go
type MockExecutor struct {
	mu            sync.Mutex
	Calls         []string
	Dirs          []string
	Err           error
	ErrFn         func(callIndex int) error
	CaptureOutput string
	CaptureFn     func(dir, command string) (string, error)
}

var _ Executor = (*MockExecutor)(nil)

func (m *MockExecutor) RunContext(_ context.Context, dir, command string) error {
	_, idx, errFn, staticErr, _ := m.record(dir, command)
	if errFn != nil {
		return errFn(idx)
	}
	return staticErr
}
```

Look at what that buys in the tests you have already seen. `Calls` is an exported slice, so an assertion is `len(mock.Calls) != 2` — no `verify(mock, times(2))`, no argument captors. `Err` makes every call fail; `ErrFn func(callIndex int) error` makes the *third* call fail, which is how "continue on failure" is tested. `CaptureFn` returns per-command output, which is how `git status` parsing is tested without a repository. And `mu sync.Mutex` makes the mock safe when `--parallel` fans out, so the concurrent paths are testable too. The `_ context.Context` parameter is worth a note: naming a parameter `_` satisfies the interface while documenting that the mock ignores cancellation.

Contrast with Java. Mockito would give you `when(...).thenThrow(...)` without writing a mock class, which is genuinely less typing. What you get in exchange is a fake that is ordinary code — readable, steppable, extensible with a new field when a test needs one, and never mysteriously failing to match an argument. Go has generators (`mockgen`, `moq`) and they are fine for wide interfaces, but for a five-method seam the hand-written fake wins.

The generalisable rule: **find the places where your domain touches the outside world — process execution, the filesystem, the clock, the network — and put a small interface at each one.** `daemon/server/monitor.go` does the same with a single function type:

```go
type BranchReader func(path string) (string, error)

func NewMonitor(configPath string, logger *log.Logger, reader BranchReader) *Monitor {
	if reader == nil {
		reader = GitBranchReader
	}
	…
}
```

One method means the interface can be a function type, and a test passes a closure:

```go
m := server.NewMonitor(cfgPath, logger, func(path string) (string, error) {
	if strings.HasSuffix(path, "/api") {
		return "main", nil
	}
	return "", errors.New("not a repository")
})
```

`nil` selects the production implementation, which is a good default-argument pattern in a language without default arguments. `io.Writer` is the third instance of the same idea: `Reporter` takes two writers rather than printing to `os.Stdout`, so one interface and one field make the entire output surface of the program assertable.

# Part 6 — Structuring a real project

## 6.1 How many modules

A **package** is a directory: the unit of compilation and visibility. A **module** is a tree of packages with a `go.mod`: the unit of versioning and dependency.

The default that serves most projects is **one module, many packages**. Nothing about having several binaries requires several modules — `cmd/zgard/main.go` and `cmd/dukh/main.go` can live in one module. Start here.

You need more when the parts are consumed independently (someone will `go get` your library without wanting your CLI, so it needs its own version tags); when they version at different rates (one `go.mod` means a dependency bump for the daemon is also one for the CLI); or when the dependency sets differ enough that you do not want them merged — grazhda's `daemon` pulls in gRPC, protobuf, a logging framework and a log rotator, and `libs` should not carry those.

grazhda chose three modules for the last two reasons plus one architectural: a module boundary is a *hard* boundary. `libs` cannot import `cli`, because `libs/go.mod` does not require it and adding that requirement would create a cycle the tooling rejects. The layering is enforced by the build, not by review convention. The cost is three `go.mod` files to keep tidy and version-skew questions between them, so do not reach for it early.

## 6.2 `go.work`

Multi-module repositories have an obvious problem: `cli` imports `github.com/vhula/grazhda/libs`, which by default resolves to a *published* version from the module proxy, so editing `libs` would not affect the CLI build until you tagged a release. `go.work`, introduced in Go 1.18, solves it:

```
go 1.26.1

use (
	./cli
	./daemon
	./libs
)
```

With that at the repository root, any `go` command inside the tree resolves those module paths to the local directories. Edit `libs`, build `cli`, done. The Maven analogy is a parent POM's `<modules>` list, with one difference: `go.work` is about *resolution*, not aggregation — it declares no shared versions and no build order.

Commit or ignore? The original advice was to gitignore it, because a workspace file is a developer's local view. In a repository whose modules only make sense together — which grazhda is — committing it is the pragmatic choice and what the project does, so a fresh clone builds with no setup. Rule of thumb: commit it if the modules are one product; ignore it if you are temporarily wiring in a dependency you happen to be editing. `go work use ./newmodule` adds an entry, and `GOWORK=off` disables workspace mode for one command — worth running in CI to check each module still builds standalone.

## 6.3 `replace` directives

`go.work` covers your machine but not someone running `go install github.com/vhula/grazhda/cli@latest`. For that, each module states the local relationship in its own `go.mod`:

```
require (
	github.com/vhula/grazhda/daemon v0.0.0
	github.com/vhula/grazhda/libs v0.0.0
)

replace (
	github.com/vhula/grazhda/daemon => ../daemon
	github.com/vhula/grazhda/libs => ../libs
)
```

The `v0.0.0` is a placeholder never resolved, because the replacement intercepts it. Three things to know: a `replace` in the **main** module applies while one in a *dependency* is ignored, so you cannot force a replacement on your consumers — which makes `replace` right for intra-repository wiring and for temporarily pointing at a local fork, and wrong as a distribution mechanism. And a module with a filesystem `replace` cannot be `go get`-ed by an outside consumer, which is fine for programs and would be a problem if `libs` were meant to be consumed externally.

## 6.4 `internal/`

A directory named `internal` anywhere in a module creates an import barrier: its packages can be imported only by code rooted at `internal`'s parent. So `libs/internal/parser` is importable by `libs/config` and `libs/workspace`, and by nothing outside `libs/` — not `cli`, not `daemon`, not any third party. It is enforced by the compiler.

This is the tool Java lacks: a public class in a library jar is public to the world whatever the Javadoc says, and Java 9 modules address it at a cost few projects pay. In Go it is a directory name. The default posture for a shared library should be: exported API in the top-level packages, everything else under `internal/`, so you can refactor freely.

## 6.5 Import cycles

Go **forbids import cycles between packages** at the compiler level, with no escape hatch:

```
package config imports github.com/vhula/grazhda/libs/workspace: import cycle not allowed
```

Java permits circular package dependencies, so most Java developers have never had to think about this and most large Java codebases have cycles they are unaware of. Go turns it into a build failure, which forces the layering to be real.

Four ways out, in rough order of preference. **Move the shared thing down** into a third package both import — `libs/path` exists for this. **Define the interface at the consumer**: because satisfaction is implicit, the package that needs a behaviour declares it and the provider never imports the consumer, which dissolves most cycles a Java developer would solve with a separate `-api` module. **Invert with a function parameter** — `BranchReader` is `daemon/server` declaring the shape of a dependency without importing whoever supplies it. Or **merge the packages**, since two that genuinely need each other may be one concept split for no reason; Go packages are allowed to be large.

The rule is per-*package*, not per-file, so two files in one directory can freely refer to each other, and an external `package foo_test` may import something that imports `foo`.

## 6.6 Where domain ends and adapters begin

grazhda's dependency direction is strictly one-way — `cli` and `daemon` both depend on `libs`, and `libs` depends on neither — and the cycle rule is what keeps it honest.

**Domain** (`libs/config`, `libs/workspace`, `libs/pkgman`, `libs/reporter`) knows about workspaces, projects, repositories and dependency order. It never calls `os/exec` (it calls `executor.Executor`), never prints to `os.Stdout` (it writes to an `io.Writer`), never reads flags, and never knows that Cobra or gRPC exist.

**Adapters** (`cli/`, `daemon/server`, `daemon/proto`, `executor.OsExecutor`) translate between the outside world and the domain. Cobra parses flags into a `RunOptions` and calls `workspace.Init`; the gRPC server converts a `Monitor` snapshot into protobuf messages. Adapters hold no rules — `daemon/server`'s package comment says so explicitly: "this package contains no domain logic of its own … it only orchestrates them on a schedule and renders the result over gRPC."

Two tests confirm the line is in the right place. Could you add a second frontend — a TUI, an HTTP API — without touching `libs/`? And can every domain test run offline, in parallel, in under a second, with no real git? For grazhda both are yes, and that is not good taste; it is what falls out of injecting `Executor` and `io.Writer` at the two places the domain would otherwise reach for the world.

# Part 7 — The libraries this project uses

## 7.1 Cobra

Cobra (`github.com/spf13/cobra`) builds command trees, and is what `kubectl`, `hugo`, `gh` and `docker` use. A command is a struct value. Here is a complete one, close to `zgard ws init`:

```go
func newInitCmd() *cobra.Command {
	var dryRun bool
	var parallel bool

	cmd := &cobra.Command{
		Use:     "init",
		Short:   "Initialize a workspace by cloning all repositories",
		Long:    "Clone every repository listed in the workspace configuration.\n\n" +
			"Repositories that already exist are skipped without error — re-running init is safe.",
		Example: "  zgard ws init\n  zgard ws init --all --dry-run",
		Args:    cobra.NoArgs,
		RunE: func(cmd *cobra.Command, args []string) error {
			return runWorkspaceOp(cmd, workspace.RunOptions{
				Context:     cmd.Context(),
				DryRun:      dryRun,
				Parallel:    parallel,
				ProjectName: projectName,
				RepoName:    repoName,
			}, "cloned", "would clone",
				func(ws config.Workspace, exec executor.Executor,
					rep *reporter.Reporter, opts workspace.RunOptions) error {
					return workspace.Init(ws, exec, rep, opts)
				})
		},
	}

	cmd.Flags().BoolVar(&dryRun, "dry-run", false, "Print actions without executing them")
	cmd.Flags().BoolVar(&parallel, "parallel", false, "Clone all repositories concurrently")
	return cmd
}
```

That command contains flag parsing, help text, and one call into `workspace.Init`. That is the whole adapter; every rule lives in `libs`.

**A factory function, not a package-level variable.** `newInitCmd()` returns a fresh command each call, which matters for testing — `daemon/cmd/cmd_test.go` calls `startCmd()` several times and inspects the result — because a package-level `var` carries flag state between tests.

**Closure-captured flag variables.** `var dryRun bool` is a local, `BoolVar` binds the flag to its address, and the `RunE` closure reads it after parsing. No struct, no field, no framework binding.

**`RunE`, not `Run`.** `Run` returns nothing and can only report failure by calling `os.Exit`, which skips every `defer` in the process. `RunE` returns an `error` that Cobra propagates out of `Execute`, where one place decides the exit code (the `errors.As` block in 3.12). Always use `RunE`.

**Persistent versus local flags.** `cmd.Flags()` registers on this command only; `cmd.PersistentFlags()` registers on this command *and every descendant*, which is where global options belong:

```go
rootCmd.PersistentFlags().BoolVar(&noColor, "no-color", false, "Disable all colored output")
rootCmd.PersistentFlags().BoolP("quiet", "q", false, "Suppress all output except errors")
```

`--no-color` now works on `zgard`, on `zgard ws` and on `zgard ws init`, defined once. The `P` suffix adds a single-letter shorthand, so `-q` and `--quiet` are the same flag; `zgard ws` uses this for `-n/--name`, `-p/--project` and `-r/--repo-name`.

**`Args` validators** check positional arguments before `RunE` runs, keeping argument-count checks out of your handler:

```go
Args: cobra.NoArgs           // reject any positional argument
Args: cobra.ExactArgs(1)     // e.g. `zgard config get dukh.port`
Args: cobra.MinimumNArgs(1)
Args: cobra.RangeArgs(1, 3)
```

Write your own when the built-ins fall short — it is just a `func(cmd *cobra.Command, args []string) error`.

**Building the tree** is `AddCommand`, and `Use: "ws"` plus the parent chain gives `zgard ws init`. Help and `--help` are generated from `Use`, `Short`, `Long` and `Example` for every node, free.

```go
cmd := &cobra.Command{Use: "ws", Short: "Workspace lifecycle commands"}
cmd.AddCommand(newInitCmd(), newPullCmd(), newStatusCmd(), newPurgeCmd())
```

**Completions** are generated from the same tree; Cobra registers the `completion` subcommand automatically, so `zgard completion zsh > "${fpath[1]}/_zgard"` works out of the box for flags and subcommand names. For values — completing workspace names after `--name` — register a function:

```go
cmd.RegisterFlagCompletionFunc("name",
	func(cmd *cobra.Command, args []string, toComplete string) ([]string, cobra.ShellCompDirective) {
		cfg, err := config.Load(configPath())
		if err != nil {
			return nil, cobra.ShellCompDirectiveError
		}
		var names []string
		for _, ws := range cfg.Workspaces {
			names = append(names, ws.Name)
		}
		return names, cobra.ShellCompDirectiveNoFileComp
	})
```

The shell invokes your binary in a hidden mode to ask, so completions are always consistent with the build. That is genuinely hard in a JVM CLI, where startup time makes per-keystroke invocation unpleasant, and it is one of the quiet arguments for writing CLIs in Go. Cobra's flag layer is `spf13/pflag`, a POSIX-style replacement for the standard `flag` package.

## 7.2 `gopkg.in/yaml.v3`

Two functions carry almost all use: `Unmarshal(in []byte, out any) error` and `Marshal(in any) ([]byte, error)`. Pass a **pointer** to `Unmarshal`; it writes through it. Fields match by `yaml:"…"` tag on exported fields, defaulting to the lower-cased field name, and `,omitempty` drops zero-valued fields on marshal.

Two behaviours to know. Unknown keys are **ignored** by default, so a typo in a config file is silent — use `yaml.Decoder` with `KnownFields(true)` for user-facing configuration. And a missing key leaves the field at its zero value, which is why `MonitoringPeriodMins` exists:

```go
func MonitoringPeriodMins(cfg *Config) int {
	if cfg == nil || cfg.Dukh.Monitoring.PeriodMins <= 0 {
		return DefaultMonitoringPeriodMins
	}
	return cfg.Dukh.Monitoring.PeriodMins
}
```

An absent `period_mins` and an explicit `period_mins: 0` are indistinguishable, because both leave the `int` at zero. Applying defaults in an accessor rather than at parse time is the standard Go answer; use `*int` only if you truly must distinguish absent from zero.

`libs/config/query.go` uses a third trick for dotted-path lookups like `workspaces.0.name`: marshal the typed config to YAML, unmarshal it back into `any`, and walk the resulting `map[string]any` and `[]any`. Round-tripping through the generic representation is much simpler than reflecting over the struct and costs nothing at CLI scale. `encoding/json` has the same shape and `json:"…"` tags.

## 7.3 `text/template`

The standard-library template engine, used for the configurable clone command:

```yaml
clone_command_template: "git clone --branch {{.Branch}} git@github.com:{{.RepoName}}.git {{.DestDir}}"
```

Rendering is parse, then execute into an `io.Writer`:

```go
func RenderCloneCmd(tmplStr string, proj Project, repo Repository, destDir string) (string, error) {
	t, err := template.New("clone").Parse(tmplStr)
	if err != nil {
		return "", fmt.Errorf("parsing clone template: %w", err)
	}
	data := CloneTemplateData{
		Branch:   EffectiveBranch(proj, repo),
		RepoName: repo.Name,
		DestDir:  destDir,
	}
	var buf bytes.Buffer
	if err := t.Execute(&buf, data); err != nil {
		return "", fmt.Errorf("rendering clone template: %w", err)
	}
	return buf.String(), nil
}
```

`{{.Field}}` reads an exported field — unexported ones are invisible, same as with YAML. The syntax also has `{{if}}`, `{{range}}` and pipelines, which is more than this project needs.

Two design points worth copying. `CloneTemplateData` exists to make the available variables an explicit, documented contract rather than "whatever happens to be in scope." And validation happens twice: at config-validation time, so a bad template is reported alongside the other errors, and again at render time.

```go
} else if _, err := template.New("").Parse(ws.CloneCommandTemplate); err != nil {
	errs = append(errs, fmt.Sprintf(
		"workspace[%d].clone_command_template: invalid template: %s", i, err))
}
```

Parsing and discarding the result is a validity check, and reporting it at `zgard config validate` time with the workspace index is much kinder than failing on the fortieth clone. Use `html/template` for anything rendered into HTML — identical syntax, plus contextual escaping.

## 7.4 gRPC and protobuf

`dukh` exposes its interface as a protobuf service, with the contract in `contracts/dukh.proto`:

```protobuf
syntax = "proto3";
package grazhda.dukh.v1;

option go_package = "github.com/vhula/grazhda/daemon/proto;dukhpb";
option java_package = "dev.grazhda.contract.dukh.v1";

service DukhService {
  rpc Stop(StopRequest) returns (StopResponse);
  rpc Status(StatusRequest) returns (StatusResponse);
  rpc Scan(ScanRequest) returns (ScanResponse);
}

message StatusRequest {
  string workspace_name = 1;
  bool   rescan         = 2;
  reserved 3 to 15;
}
```

Both `go_package` and `java_package` are there because grazhda's third component is a Spring service — one contract, two generated clients, which is much of the argument for protobuf over hand-written JSON.

Code generation is a build step, not a library call:

```bash
$ go install google.golang.org/protobuf/cmd/protoc-gen-go@latest
$ go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@latest
$ protoc --go_out=. --go-grpc_out=. \
         --go_opt=module=github.com/vhula/grazhda/daemon \
         --go-grpc_opt=module=github.com/vhula/grazhda/daemon \
         contracts/dukh.proto
```

`protoc-gen-go` emits the message structs, `protoc-gen-go-grpc` the client and server interfaces, both into `daemon/proto`, and both are **committed to the repository** — the normal Go convention, so a plain `go build` works without protoc installed. Unlike Maven's protobuf plugin, nothing in `go.mod` triggers generation, because Go's build has no plugin phases. Less magic, more explicit steps, and a real risk of a stale generated file that CI should catch by regenerating and failing on a diff.

Implementing the server is the embedding pattern from 3.9:

```go
func (s *Server) Serve(lis net.Listener) error {
	gs := grpc.NewServer()
	dukhpb.RegisterDukhServiceServer(gs, s)
	s.grpcServer.Store(gs)
	s.logger.Info("dukh: gRPC server listening", "addr", lis.Addr().String())
	return gs.Serve(lis)
}
```

Every handler takes a `context.Context` first, cancelled when the client goes away — which is why the `TriggerScanAndWait(ctx)` machinery in 4.5 exists. The client side is a dialled connection wrapped in a generated stub:

```go
func Dial(addr string) (*grpc.ClientConn, error) {
	conn, err := grpc.NewClient(addr, grpc.WithTransportCredentials(insecure.NewCredentials()))
	if err != nil {
		return nil, fmt.Errorf("cannot create dukh client for %s: %w", addr, err)
	}
	return conn, nil
}
```

`grpc.NewClient` is lazy: it returns immediately and connects on first use, so `zgard ws status` against a stopped daemon fails at the RPC with a clear error rather than at dial time. `insecure.NewCredentials()` is explicit about running unencrypted on loopback — gRPC makes you say so rather than defaulting to it. The caller closes the connection, typically with `defer conn.Close()`.

Compared to Spring: no `@GrpcService`, no component scan, no application context. You construct a `grpc.Server`, register a struct on it, and call `Serve` on a listener you opened. The wiring is code you read top to bottom.

## 7.5 `io.Writer` as the universal seam

Worth stating on its own, because it is the most reused idea in the project. One method — `Write(p []byte) (n int, err error)` — satisfied by `os.Stdout`, `*os.File`, `net.Conn`, `*bytes.Buffer`, `*strings.Builder`, `gzip.Writer`, `http.ResponseWriter`, and the log rotator the daemon writes to.

`Reporter` takes two of them. Production passes `os.Stdout` and `os.Stderr`; tests pass two `*strings.Builder`s; a future `--log-file` passes an `*os.File`; an HTTP frontend passes an `http.ResponseWriter`. None of that requires `reporter` to change. Everything writes through the `F` variants, which take a writer as their first argument:

```go
fmt.Fprintln(r.out, line)
fmt.Fprintf(r.errOut, "      %s\n", clr.Red(res.Repo+": "+res.Err.Error()))
```

The habit to build: **a package should almost never call `fmt.Println`.** Take an `io.Writer`. It costs one field and makes the package testable, embeddable and redirectable forever. Its mirror `io.Reader` has the same shape and the same reach, and `io.Copy`, `io.ReadAll`, `bufio.Scanner` and `io.MultiWriter` compose over the pair. If you learn one idiom from the standard library, learn this one.

# Part 8 — Idioms, gotchas and a cheat sheet

## 8.1 Accept interfaces, return structs

**Accept interfaces** in parameters, so callers can substitute: `func New(out, errOut io.Writer) *Reporter`, `func Init(ws config.Workspace, exec executor.Executor, …) error`. **Return concrete types**, so callers get the full API and can see what they have: `*Reporter`, `*Monitor`, `*Config`. Returning an interface hides methods for no benefit, prevents callers adding their own type assertions, and creates the nil-interface trap from 3.8. The one universal exception is `error`, always returned as the interface.

The corollary: **define the interface where it is consumed, and keep it small.** Do not write one until you have a second implementation or a test that needs a fake. A one-implementation interface with the same name as its implementation plus `Impl` is the Java habit, and in Go it is dead weight.

## 8.2 Make the zero value useful

`var wg sync.WaitGroup`, `var mu sync.Mutex`, `var buf bytes.Buffer`, `var sb strings.Builder`, `workspace.RunOptions{}`, `config.Config{}` — all immediately usable. When designing a type, ask what `var x T` should mean and try hard to make it correct. It removes constructors, removes an initialisation error path, and makes struct literals pleasant. Where it cannot work — a `Reporter` needs writers, a `Monitor` needs channels made — write a `New…` function and make it the only way to build a valid value by keeping fields unexported.

## 8.3 nil slices and nil maps

```go
var s []string
len(s)              // 0
for range s { }     // zero iterations
s = append(s, "x")  // works — append allocates

var m map[string]bool
m["x"]              // false — reads are fine
m["x"] = true       // PANIC: assignment to entry in nil map
```

A nil slice behaves like an empty one everywhere except identity, and `Validate` relies on it: `var errs []string`, appended to only when something is wrong, with the caller checking `len(errs) == 0`. No initialisation, no null check, and the happy path never allocates. A nil map accepts reads but not writes, so any map you will write to needs `make`.

Do not write `if s != nil && len(s) > 0`; `len(s) > 0` covers both. And do not work to return an empty non-nil slice instead of nil — callers should not care. The one place it matters is JSON, where a nil slice marshals to `null` and an empty one to `[]`.

## 8.4 Shadowing in `if err := f(); err != nil`

The `if` statement takes an optional init statement, and what it declares is scoped to the `if` and its `else`. Use it whenever you need a value only for the check:

```go
if err := yaml.Unmarshal(data, &cfg); err != nil {
	return nil, fmt.Errorf("parsing config %q: %w", path, err)
}
if idx := strings.LastIndex(name, "/"); idx >= 0 {
	return name[idx+1:]
}
if n := CountMatchingRepos(ws, opts); n > 1 {
	rep.PrintWarn(fmt.Sprintf("Warning: --repo-name %q matches %d repositories", opts.RepoName, n))
}
```

**The shadowing bug.** Because `:=` declares, an inner `err` can hide an outer one:

```go
func load() (*Config, error) {
	var cfg *Config
	var err error
	if useFile {
		cfg, err := config.Load("a.yaml")   // BUG: := declares NEW cfg and err
		…
	}
	return cfg, err                        // always nil, nil
}
```

The compiler will not warn, because both inner variables are used. The habits that prevent it: use `=` when both variables already exist, keep `err` scoped to the `if` where you can, and run the `shadow` vet tool. Most importantly, if a function is deep enough for this to happen, it is deep enough to split.

## 8.5 Map iteration has no order

Every run visits a map's keys in a different order, by design — the runtime randomises the starting offset specifically so that code accidentally depending on order fails immediately and locally rather than in production on a different Go version. If output must be deterministic, sort:

```go
var queue []string
for id, deg := range inDegree {
	if deg == 0 {
		queue = append(queue, id)
	}
}
sort.Strings(queue)
```

`pkgman.Resolve` does this at every step of its topological sort, and again for the cycle-report list. Without it, `zgard pkg install` would install packages in a different order every run — exactly the class of bug randomisation exists to surface. The same applies to test assertions over map contents: collect, sort, compare.

## 8.6 Common compile errors and what they mean

**`declared and not used: cfg`** — you declared a variable and never read it, and the build fails rather than warning. Delete it, or assign to `_` if you need the call's side effect. Function parameters and package-level variables are exempt. The one that catches everyone: commenting out a line during debugging removes the only use of a variable, and now the code will not compile. That is the language insisting you clean up as you go. `"fmt" imported and not used` is the same rule for imports; `goimports` on save makes it stop happening.

**`cannot use x (variable of type T) as U value`** — Go's assignability rules with no implicit conversion, in two flavours. Named types are distinct even with the same underlying type, so `time.NewTimer(somePlainInt)` fails and you convert with `time.Duration(period) * time.Minute`. Or an interface is not satisfied, and the message says why: `MockExecutor does not implement Executor (method Run has pointer receiver)` means use `&MockExecutor{}`, while `missing method RunCapture` means a typo or a mismatched signature.

**`assignment mismatch: 2 variables but f returns 1 value`** — check the signature; there is no overloading, so there is only one.

**`missing return`** — a function with a result type has a path reaching the end. Go's terminating analysis is syntactic: a `for {}` with no `break` counts as terminating, but an `if`/`else if` chain without a final `else` does not, even if you can prove it covers every case.

**`invalid operation: x + y (mismatched types int and int64)`** — no implicit numeric promotion. Convert explicitly.

**`fatal error: all goroutines are asleep - deadlock!`** — runtime, not compile time. Usually an unbuffered channel with no receiver, a `wg.Wait()` where some `Done` is never reached, or a `select` with no ready case. The dump lists every goroutine and where it is blocked; read it from the bottom.

**`panic: assignment to entry in nil map`** — you forgot a `make` (3.11). **`panic: runtime error: index out of range [3] with length 3`** — the message names both the index and the length, usually enough without a debugger.

## 8.7 Small things worth knowing

`%q` in error messages quotes and escapes, making empty and whitespace values visible; use it for anything user-supplied. `_ = someFunc()` documents an intentionally ignored error. A package's doc comment goes immediately above `package x` with no blank line and starts with the package name; exported identifiers get a comment starting with their own name, which is the linted convention and makes generated docs read as sentences. `go doc github.com/vhula/grazhda/libs/workspace RunOverRepos` prints documentation from the command line, offline. `struct{}{}` is the zero-size empty struct value, so `map[string]struct{}` is a set storing no values. Build constraints select files by platform, either by filename suffix (`detach_unix.go`, `detach_windows.go` in `daemon/cmd`) or with a `//go:build linux || darwin` first line. `//go:generate` comments record generation commands next to the code. `t.Log` output only appears with `-v` or on failure, and `go clean -testcache` helps when you suspect the cache is lying to you.

## Where to go next

Read the standard library's source. It ships with your toolchain, it is the reference for idiomatic style, and it is unusually readable — `strings/builder.go`, `errors/wrap.go` and `sync/waitgroup.go` are each worth twenty minutes.

Then three documents, in order: *Effective Go*, the *Go Code Review Comments* page, and the release notes for every version since the one you learned on. The language changes slowly enough that reading them all is a short afternoon, and the Go 1.22 loop-variable change alone will save you an argument.

Then write `zgard ws status`. It targets a workspace, fans out over repositories, calls an injected executor, reports through an `io.Writer`, and returns an error. That one command exercises nearly everything in this guide.
